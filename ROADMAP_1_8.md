## Приоритет 1 — качество результата и короткий путь пользователя

1. **Очередь проверки кадров.** Считать для соседних кадров сдвиг центра и площади силуэта, внезапную пустоту, скачок опоры, близость к краю, разрыв между началом и концом цикла, низкую уверенность маски/привязки. Показывать миниатюры только подозрительных кадров с переходом к исправлению. Порог должен быть настраиваемым, предупреждение не должно автоматически выкидывать кадр. В `makeReport()` сейчас есть лишь скачок ширины/высоты более 20%, касание края и позднее добавляемые предупреждения трекеров.
2. **Коррекция края с проверкой на разных подложках.** Сейчас ИИ-маска нормализуется отдельно на каждом кадре, бинаризуется и размывается; RGB у края не восстанавливается. Начать с тестов белого/чёрного ореола, мягкой альфы и временной стабильности, затем внедрить управляемое уточнение альфы и коррекцию загрязнённого цвета. Кнопка «до/после» и пять подложек позволяют проверить результат. Не применять к пиксель-арту без явного выбора.
3. **Опора и хитбокс как данные.** Сейчас pivot для `ground` зависит от нижнего отступа ячейки; прямоугольник по альфе рисуется в игровом превью, но отсутствует в manifest. Добавить per-frame bounds/hitbox, координаты в целой ячейке, затем пользовательскую настройку опоры и отдельный вариант вычисления по ступням/контакту с землёй. Проверить, что обрезка и масштаб атласа сохраняют правильные координаты во всех экспортерах.
4. **«Авто» с понятным отчётом.** Один запуск применяет существующие рекомендации, строит превью и открывает очередь проверки. Экспорт в выбранную папку запускается после просмотра проблемных кадров. Показывать, какие значения выставлены автоматически, и разрешать откат каждого решения.
5. **Точный выбор фрагмента видео.** Текущие два ползунка/поля уже задают начало и конец; добавить ленту миниатюр, курсор кадра, клавиши шага по кадрам и точное время. Проверять граничные условия переменного FPS.
6. **Недавние проекты и восстановление путей.** Показывать 5–10 `.cslab` с меткой наличия исходников и быстрым переназначением папки. Хранить только локальные метаданные, с явным удалением из списка.

## Приоритет 1 — ремонт готового спрайт-листа и согласование кадров

**Актуальный статус:** автоматический поиск и изоляция объектов, ручные прямоугольники с координатами, визуальная сетка и пересборка листа с JSON уже работают. Пункты ниже — исходная постановка и развитие для слипшихся фигур, опорных точек и контроля качества; клубок больше не является невыполненной задачей.

Это отдельный рабочий сценарий, добавленный по двум реальным проблемам пользователя. Он должен работать с PNG-листом и, если он есть, с исходным JSON, не перезаписывая оригиналы. Текущий `sliceSpriteSheet()` умеет искать объекты по компонентам/цвету либо разрезать равномерную сетку; он сразу сохраняет найденные прямоугольники как кадры. Интерфейс позволяет выбрать один из двух режимов и пересчитать лист. Между обнаружением и разрезкой пока нет редактора границ. Покадровая трансформация есть, но ползунки масштаба не согласуют персонажа по серии автоматически. Кроме того, включённая по умолчанию опция `sheetFitEach` может увеличивать маленький кадр сильнее соседних.

### A. Найти и разнести объекты

1. Загрузить лист и прочитать существующие координаты, имена, порядок, длительности и pivot из JSON, если его формат известен. Показать поверх листа **старые ячейки и реальные контуры объектов** разными линиями. Отдельно отметить пиксели объекта за границей назначенной ему ячейки и пиксели чужого объекта внутри ячейки.
2. Предложить объекты автоматически по маске альфы либо по цвету фона и связным областям. Для отделённых деталей одного кадра дать команду «объединить», для двух объектов в одной области — «разделить». Предусмотреть несколько предложений при неуверенности; нельзя молча выбирать между наложившимися объектами.
3. Ручной режим: тянуть прямоугольник или лассо, менять координаты `x/y/w/h` численно, назначать объект кадру, добавлять/удалять кадры и менять порядок. Подложки белая/чёрная/зелёная/маджента помогают видеть край.
4. Автопереупаковка создаёт новые независимые кадры с прозрачным запасом вокруг полного силуэта, выбранным минимальным зазором, одинаковой опорой и новым листом. Новый JSON хранит `frame`, `sourceSize`, `spriteSourceSize`, pivot, тег и длительность, а также происхождение кадра на исходном листе. При несовместимости движка можно экспортировать отдельные PNG и профильный JSON.
5. Контроль перед сохранением проигрывает анимацию и проверяет: ни один непрозрачный пиксель не срезан; внутрь кадра не попали пиксели соседнего объекта; элементы не пересекаются в новом листе. Если объекты в исходном растре соприкоснулись или перекрылись без различимой границы, показать конфликт для ручного решения — исходные скрытые пиксели восстановить невозможно без отдельной генеративной дорисовки.

**Проверенный пример — клубок.** `public/images/monya-dream/props/yarn-ball-roll-and-guide-6-frame-v2-review.png` имеет размер 1536×1024, его старый JSON задаёт сетку 3×2 по 512×512. Лист непрозрачный, с белым фоном. Старые ячейки резали длинную нить и захватывали соседний кадр. Текущий режим поиска объектов на этом исходном файле нашёл 6 отдельных областей; полный прогон создал новый лист и JSON с 6 кадрами, исходными координатами и именами. Новый лист просмотрен: все шесть объектов и нити видны. Это проверка возможности инструмента, а не замена игрового файла: игровой код использует фиксированные прямоугольники, поэтому для подключения нового листа ему понадобится чтение нового JSON или обновление координат.

### B. Выровнять размер и контур серии

1. Разделить **выравнивание масштаба/позиции** и **правку формы**. Для выравнивания использовать устойчивую часть персонажа (туловище/центр массы/точка контакта), а не полный bounding box: крылья, вытянутые лапы и другие изменения позы меняют прямоугольник, хотя размер героя тот же. Предложить опорный кадр, общий pivot и масштаб каждого кадра; пользователь видит числа и может закрепить кадр вручную.
2. Показать все кадры поверх опорного с полупрозрачным наложением, контуры в разных цветах, графики масштаба/положения и предупреждения о резких скачках. Кнопки: «выровнять серию», «исправить этот кадр», «применить к выбранным», «вернуть исходный». Блокировать растяжение по одной оси по умолчанию; для пиксель-арта предлагать только целочисленный масштаб и nearest-neighbor.
3. Ручная правка внутри кадра: кисть/ластик альфы, лассо, перемещение выделенного фрагмента, коррекция края и undo/redo. Работать на копии исходника с сохранением истории в проекте.
4. Помощь ИИ: предлагать маску и соответствующие точки/части между кадрами, отмечать низкую уверенность, сглаживать случайное мерцание контура без усреднения нужной анимации. Генеративная дорисовка должна быть отдельным явным действием с просмотром до/после; она не должна менять утверждённую внешность героя или добавлять детали без проверки пользователя.
5. После исправления повторять проверку на обрезку, соседние пиксели, скачки размера и сохранность опорной точки, затем собирать новый PNG и JSON. Измерять масштаб именно по устойчивой части тела, а не требовать одинаковых габаритов разных поз.

**Реальный приёмочный пример — светлячки.** `public/images/monya-dream/characters/firefly-flight-3-frame-spritesheet-review.png` имеет три ячейки 724×724. По альфе габариты силуэтов в них около 605×366, 487×482 и 527×309 пикселей. Это само по себе не доказывает ошибочный масштаб, потому что положение крыльев различается; тест должен сравнить размер тела и опорные точки при проигрывании. Результат — визуально постоянный размер тела, сохранённый взмах крыльев и корректные координаты кадров в новом JSON.

| --- | --- | --- |
| Ограниченный пул обработки кадров | Замер показывает, что последовательный цикл `buildAnimation()` доминирует | Разделить независимую очистку на пул 2–4 кадров с лимитом памяти; затем строго упорядочить результаты перед дедупликацией, отчётом и экспортом. Отмена должна останавливать задания. |
| Инкрементальный предпросмотр | Пользователь часто меняет один параметр и ждёт полную сборку | Кэш по стадиям: извлечение → маска/правки → привязки → нормализация → атлас. Изменение сетки не пересчитывает маски, правка одного кадра не пересчитывает остальные. Не хранить бесконтрольно сырые RGBA. |
| Вычисление границ кадра вне UI | Профиль показывает заметные зависания при первом показе крупных кадров | `frameBounds()` сейчас кэширует результат после первого сканирования. Лучше передавать bounds, уже вычисленные процессором, либо делать однократный расчёт в worker. |
| DirectML или WebGPU | Реальный прогон конкретной модели стабилен на целевых GPU и быстрее CPU с учётом передачи данных | Прототип отдельного пути с CPU fallback, самодиагностикой и тестом упаковки portable EXE. Для DirectML не запускать `Run` параллельно на одной сессии. Показать скорость по этапам, без общей цифры «5–20×» до замера. |

Canvas 2D и WebGL сравнивать на реальной анимации только после профилирования. Простая замена движка предпросмотра без измеренного узкого места не имеет приоритета.

## Приоритет 3 — расширения после устойчивого ядра

- **Модели «быстро/точно».** Сравнить U²-Netp с разрешёнными для распространения моделями на собственном наборе кадров; учитывать качество волос/меха, мерцание по кадрам, скорость, память и размер portable EXE. BiRefNet — кандидат для прототипа. RMBG-2.0 требует отдельного коммерческого соглашения для коммерческого применения; автоматически встраивать её в релиз нельзя.
- **Ручные инструменты маски.** Пипетка для однородного фона и лассо/прямоугольник поверх уже существующей «умной области» и кисти. Добавить «применить правку к соседним кадрам» с предпросмотром и уровнем уверенности трекинга.
- **CLI и пакет из папок кадров.** Вынести конфигурацию сборки в версионированный JSON-профиль, использовать тот же движок для GUI и команды; предусмотреть коды выхода, machine-readable отчёт, dry-run, конфликт имён и остановку без частичного результата.
- **Импорт Aseprite и дополнительные экспортеры.** Делать по реальному целевому пайплайну игры. Перед импортом нужны сохранение тегов, длительности, слоёв и точек опоры; перед новым экспортером — эталонный проект в конкретном движке. GIF/APNG как форматы показа, а не замена игровому PNG/JSON.
- **Ассистент.** Сначала детерминированная палитра команд на естественном русском: текст разбирается в проверяемые настройки, каждое действие показывается до применения и может быть отменено. Локальную LLM оценивать только после набора типовых запросов и метрики ошибочных действий. Возможность API отдельно от локального режима и с ясной политикой передачи данных.
- **Экспериментальные LaMa/RIFE/апскейл.** Отдельные переключаемые модули, без установки по умолчанию. Для пиксель-арта и покадровой анимации возможны изменения формы и мерцание; сравнивать с эталонными кадрами и оценивать лицензии/размер модели.

## Мои дополнительные предложения

1. **Повторяемый экспорт.** В отчёт записывать версию приложения/модели, настройки, подписи исходников и контрольные суммы результата. Это поможет понять, почему два спрайт-листа отличаются и правильно восстанавливать проекты.
2. **Проверка атласа в контексте движка.** Встроенный инспектор: при наведении показывать номер страницы, прямоугольник, тег, длительность, trim и hitbox; отдельная кнопка проверяет ограничения выбранного экспортного профиля.
3. **Бюджет ресурсов.** Видимая оценка времени, требуемой памяти, размера промежуточных файлов и выходного атласа до сборки; безопасное ограничение числа кадров и план разбиения до запуска.
4. **Регрессионный набор визуальных эталонов.** Синтетические случаи для логики и утверждённые пользователем реальные кадры для сравнения края/временной стабильности. Тесты по пикселям там, где результат детерминирован; рядом — ручная оценка сложных случаев. Автоматически не перезаписывать эталоны.
5. **Плавное восстановление после сбоя.** Атомарная запись `.cslab`, несколько локальных снимков с ограничением диска и понятное восстановление последней рабочей версии. Автоматические git commit/push проекта не нужны без явной настройки пользователя.
6. **Масштаб UI и доступность.** Проверить 125–200% Windows DPI, узкое окно, клавиатурный фокус, контраст, длинные русские подписи и модальные окна. Это полезнее ранней разработки светлой темы.

## Контрольные ворота

1. **После приоритета 0:** одинаковый экспорт из неизменного проекта, отсутствие роста временного каталога при настройке, диагностируемый старт portable EXE.
2. **После приоритета 1:** на эталонных проектах пользователь находит плохие кадры из очереди проверки, а hitbox/pivot совпадают с результатом в игре.
3. **После приоритета 2:** ускорение подтверждено сравнением одинаковых входов на той же машине, память и число сбоев не выросли.
4. **Для любой новой модели:** лицензия допустима, файл модели проверяется контрольной суммой, поддерживается CPU fallback и есть сравнение качества с текущей моделью.
